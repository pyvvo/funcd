# FEAT-0000: V1 — Agent-ready core

- **Status**: Active (living document — the tracking table updates as ADRs progress)
- **Date**: 2026-06-13
- **Deciders**: green-0-rabbit
- **Defines**: V1 scope · outlook for V2/V3

## Initial need

In an AI era where agents are becoming common, there is no lightweight way to deploy and
run agents/functions on **one Linux machine** without adopting Kubernetes or Docker:
existing FaaS platforms are either cloud-locked, cluster-shaped, or capped. funcd answers
that need: a modular, single-binary, API-first serverless platform ([blueprint.md](../../blueprint.md))
that deploys, runs, exposes, monitors, and administers functions and agents with low
resource consumption, strong observability, and a clean path to multi-node later.

Agents are the defining workload: they are event-driven, bursty (scale-to-zero matters),
and **stateful through platform services** — a V1 that cannot persist state or hold a
secret cannot run a real agent. That is why V1 is the *agent-ready core*, not a bare FaaS.

## How this document works

This file captures **what** must exist per version — high level only. The **how** lives
in ADRs (`docs/adr/`, process in [ADR-0000](../adr/0000-adr-process.md)): every feature
below maps to one or more ADRs; no implementation detail belongs here. Feature status:
`idea → adr → accepted → reviewing → implemented`.

## V1 — Agent-ready core

**Exit criterion**: on a fresh Linux box, one binary + systemd unit; a user can
`funcdcli apply` a JavaScript or Python function **from a source artifact** (no
Dockerfile, no registry push) whose handler consumes CloudEvents, reads a secret,
persists state in the KV service, is invoked over HTTP and by a timer, scales to zero
when idle and wakes on demand — all observable, all through the public API/CLI.

### Explicitly out of V1

Strong isolation (Kata microVM → V3; the gVisor tier was dropped 2026-06-13 — runc with
conservative OCI defaults is the only container isolation until V3, WASM covers untrusted
code by construction), full egress control (L7 capture/`EgressPolicy` → V2; V1 ships only
lateral default-deny in F12), **arbitrary OCI-image functions** (curated JS/Python
runtimes only — "bring your own image" comes later behind the same Runtime port), WASM
runtime, workload-identity IAM (SPIFFE-style tokens, `Grant` *enforcement*, cedar — note
the `Grant`/`EgressPolicy` resources exist in F03 but are not yet enforced in V1),
vector/graph/workflow services, config service, async invocation queue, slatedb driver,
Terraform provider, quotas, rollout/canary traffic splitting, multi-node.

## V2 outlook — Hardened & full-service (to be scoped in FEAT-0001 when V1 nears its exit criterion)

Candidates: egress control enforcement (network manager: nftables default-deny,
transparent egress gateway — TPROXY + SNI peek + DNS-aware policy, capture/audit of all
outbound TCP incl. databases, `EgressPolicy` enforcement) · WASM runtime (also the
isolation tier for untrusted code — gVisor dropped 2026-06-13) · internal IAM (workload
identity, `Grant` enforcement, cedar-go PDP) · **Terraform provider** (`terraform-provider-funcd`
over the control-plane API + API keys) · config service · OpenBAO-backed secrets driver ·
full eventing (sources, sensors, triggers, CloudEvents) · async invocation · workflow
engine (NATS-based) · slatedb store driver (on the storage layer) · per-namespace quotas ·
`Revision` traffic split / canary · audit hardening · more curated runtimes and/or
arbitrary OCI-image functions (timing open).

## V3 outlook — Scale-out & ecosystem

Candidates: **Kata microVM runtime class** (Dragonball → Cloud Hypervisor fallback;
deliberately deferred from V2 on 2026-06-13) · multi-node (worker registration over NATS,
placement, mTLS) · autoscaling policies (concurrency/RPS) · function build pipeline
(source → OCI/wasm) · registry cache + signature verification (cosign) · vector & graph
services · crypto service · MCP/gRPC exposure · pre-warmed pools / VM snapshot cold-start
mitigation.
