# FEAT-0001: v1.1 — Statically-defined function I/O contracts

- **Status**: Active (living document — the tracking table updates as ADRs progress)
- **Date**: 2026-06-19
- **Deciders**: green-0-rabbit
- **Defines**: v1.1 scope (typed, statically-inspectable event input/output contracts) · positions V2 as FEAT-0002

## Initial need

V1 ([FEAT-0000](0000-feat-v1.md)) shipped an **opt-in event-data contract** (F26 / [ADR-0038](../adr/0038-event-data-contract-jtd.md)):
an author **hand-writes** a JTD schema for a CloudEvent's `data`, it ships *in* the artifact (digest-pinned), and the
runtime shim rejects a wrong-shaped event **before** the handler runs. Three gaps remain for the contract to be
genuinely useful:

1. **The schema is hand-written and can drift** from the author's actual type (`Handler<In>` in TS, a class in
   Python) — the type is compile-time only; the schema is a *second, hand-maintained* copy.
2. **There is no output contract** — only the incoming `event.data` is checked, never the handler's result.
3. **The schema is buried inside the artifact bundle** — to read it you must fetch and parse the bundle (or run it).
   It is not **statically inspectable**: a registry, a deploy-time policy, or an agent cannot read a function's I/O
   contract *without pulling and executing the artifact*.

v1.1 closes all three: **the author's code type is the single source of truth**, the contract is **generated from it**
as **JSON Schema** (input *and* output) at push time, validated in the sandbox by an **eval-free, precompiled**
validator, and surfaced as **OCI manifest metadata** so any tool can read a function's contract without running it.
JSON Schema (not JTD) is the canonical format — it is what the mature type→schema generators emit (typia for TS,
pydantic for Python), it keeps the author's full validation (formats/ranges/patterns), and it is the format the future
contract-registry / policy layer speaks natively. This is a backward-compatible, additive increment — a **minor**
version (1.1.0), not the V2 architectural epoch.

## v1.1 — Statically-defined function I/O contracts

**Exit criterion**: an author declares a function's event **input and output** shape as ordinary code types — a
TypeScript interface/type, or a Python class — with **no hand-written schema**; `funcdcli push` **generates** the
canonical **JSON Schema** contract from those types, ships an **eval-free precompiled validator** in the bundle, and
**embeds the JSON Schema as OCI manifest metadata** on the function artifact; the contract is **readable straight from
the artifact's manifest without pulling the bundle layer or running the code**; and the runtime shim validates
incoming `event.data` against the input contract **before** invoke (V1 behavior, faster + eval-free) and the handler's
**result** against the output contract. Opt-in and backward-compatible: a function with no declared types behaves
exactly as in V1.

## v1.1 — Platform extensibility & inter-function calls (added track)

A **deliberate, decider-approved expansion** of v1.1 beyond the original contract theme (above): two features
that turn funcd's implicit, ungoverned fn-to-fn HTTP calls into a **declared, validated, traced** capability —
plus the generic admission seam that makes it (and future cross-resource policy) possible. Same minor version;
additive and backward-compatible. The **V2 multi-node** transport (over the NATS lattice, for callees on a
different worker node / network) is explicitly deferred to FEAT-0002.

## Out of scope (tracked elsewhere)

- **Contract registry + AI-proposed compatible artifacts + deploy-time admission policy** — the layer *on top* of
  F30's statically-readable contracts (match one function's output schema to another's input; reject a non-conforming
  artifact at deploy). Tracked on the GitHub **Project #4** backlog (toward V2); not a v1.1 ADR.
- **JTD** — superseded by JSON Schema as the canonical contract format (ADR-0058 supersedes ADR-0038). No JTD↔JSON-Schema
  conversion is in scope (the type → JSON Schema path is direct; JTD is simply retired for the contract).
- **tmpfs / large-payload contracts, schema versioning/evolution, contract negotiation** — later.

## V2 outlook — Hardened & full-service (FEAT-0002)

The V2 architectural epoch (egress enforcement, microVM/WASM isolation — incl. the **krun-via-crun** sandbox runtime
tracked on Project #4 — internal IAM / `Grant` enforcement, full eventing, async invocation, multi-node, distro
packaging) is scoped separately as **FEAT-0002**, when v1.1 lands. See [FEAT-0000](0000-feat-v1.md)'s V2/V3 outlook for
the candidate list; v1.1 is the small contract increment between them, not that epoch.
